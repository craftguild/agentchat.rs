# Synthetic workloads

The Runtime workload targets use controlled native adapters to measure local application behavior. They do not measure a real model's inference latency or certify native engine startup. Ordinary short smoke profiles check functionality; strict profiles retain fixed rates, populations, persistence and resource audits.

Inspect runner options before using a new owned result directory:

```sh
python3 tools/run-workload.py --help
python3 tools/run-viewer-workload.py --help
```

The current full-input and legacy hint profiles have separate source/image and measurement scope. Do not add their overlapping counts or treat a legacy hint fixture as the current native body route.

## Measurement and enforcement

Commit-return and first local native-dispatch timestamps use their original measurement boundaries. Keep every selected sample, including unknown/failed auxiliary observations. Inclusive overlapping method sums are not exclusive wall time, CPU time or per-Post causal attribution.

macOS strict runs enforce absolute latency/posting-window targets. Linux retains the actual numbers and independent target flags, including false, with `timing_enforced=false`. Strict functional profiles remain enabled on Linux. There is no coefficient calibration or baseline-update framework.

Both platforms require complete accounting, immutable bodies/recipients, original authority and FIFO, FULL stop/reopen integrity, bounded queues/jobs, log rotation, per-process resources and stop/hang detection. An exit-zero Linux run does not mean the numerical target passed. Failed, partial and cancelled originals retain their status. See [verification](verification.md) and [ADR 0012](../adr/0012-macos-performance-and-runtime-simplicity.md).
