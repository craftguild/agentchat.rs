# ADR 0018: Launch-owned, ordered full-body delivery

## Status

Accepted and implemented, with recorded verification qualifications. Later scope is amended or superseded by [ADR 0025](0025-agentchat-naming-and-explicit-launch-participation.md), [ADR 0027](0027-process-continuity-across-executable-updates.md), [ADR 0028](0028-managed-auto-join-and-conversation-following.md), [ADR 0032](0032-delivery-state-machine-and-ack-removal.md).

This record retains the decision's context, alternatives and consequences. Read it with the [current contracts](../README.md) and [verification scope](../guides/verification.md). Historical execution records are preserved separately; they do not certify arbitrary newer images or authorize installation, state replacement or publication.

### Accepted selective-channel follow-up, 2026-10-26

[ADR 0029](0029-autonomous-collaboration-and-channel-scopes.md) supersedes all-channel enrollment with configured mandatory defaults and explicit membership elsewhere. Agent content reads, events and delivery share the same scope; human observers retain all-history access. This preserves the original owner and unknown-head fences while separating concurrent collaboration spaces.

### Accepted managed conversation-following follow-up, 2026-10-26

[ADR 0028](0028-managed-auto-join-and-conversation-following.md) supersedes the fixed-root/no-proxy restriction and unjoined startup. Exact verified same-project foreground switches follow the selected conversation through a byte-transparent lifecycle observer. This avoids continuing input into a hidden old root. No old backlog or authority transfers to a new root; same-root Leave persists.

### Implemented process-continuity follow-up, 2026-10-26

[ADR 0027](0027-process-continuity-across-executable-updates.md) separates ongoing boot/PID/kernel-start/user continuity from mutable executable identity. Initial selection and filesystem checks remain independent. A compatible replacement must not falsely imply original-owner loss; first adoption from older loaded code still needs normal restart.

### Accepted explicit-participation follow-up, 2026-10-23

[ADR 0025](0025-agentchat-naming-and-explicit-launch-participation.md) introduced the AgentChat name, managed-launch authorization and explicit Join/Leave/rejoin. Same-UUID frontends share the original managed owner's lifetime; a surviving frontend alone cannot retain authority after that owner is lost. ADR 0028 later amends startup and conversation following without weakening this owner fence.

### Accepted Codex simplification, 2026-10-22

The accepted simplification removed the earlier Codex relay and used direct native app-server connections for ordered complete-body input. It retained conversation-level authorization, original managed process lifetime and native controls rather than introducing per-frontend exclusivity. This was the selected implementation for that stage, not proof of arbitrary host behavior. ADR 0028 later reintroduces only byte-transparent lifecycle observation for exact root following, superseding the fixed-conversation restriction.

### Implemented contract and historical evidence

The implementation was verified in separately scoped engineering and native stages, retaining failed/partial cases and original source/image qualifications. Those records are preserved separately. The [current verification summary](../guides/verification.md) distinguishes these observations from operational adoption and newer images.

## Context

Codex can retain a conversation after its CLI exits, and successful inputs can extend that retention. Shared-server MCP identifies the conversation but does not establish which frontend made a call. Claude file writes can also succeed after its CLI dies. Neither successful output nor a surviving server/helper establishes that the intended CLI still exists.

The user selected launch-owned process lifetime as the independent delivery boundary, direct full-body reception instead of a preview/body-fetch exchange, and one ordered stream per receiving conversation. These decisions remove the need to discover arbitrary already-running frontend PIDs or wait for native server cache expiry. Remaining implementation and native control checks still need evidence; they are not unresolved choices of delivery architecture.

## Decision

### 1. Launch and membership

Use `ac launch codex` and `ac launch claude` as native participation entry points. The launcher binds the exact host conversation ID, project, native CLI process identity and fresh launch generation. Establish membership outside the model before its first user prompt needs AC, after normal host trust and integration initialization. A spawned process alone is not a completed startup handshake.

Native launch uses a fresh actor rather than inherited/supplied AC_CONTEXT; remove that inherited actor descriptor from the child environment. Normal configuration discovery must match the inspected owned bundle. An isolated tool-only layout cannot silently fall back to the real native profile. Preserve the host's own interruption behavior while the original supervisor lives; a requested process termination acts only on its owned unreaped child. Record actual native exit before reconciling generation loss.

Resolve the installed native bundle through the existing ownership inspection lock before managed startup. An intact owned selector and every required current AC component must agree; a foreign, changed, partial, stale or pending setup is not a launch source. Read-only planning cannot repair settings, execute a host, establish readiness or admit a profile. Actual native identity, initialization, controls and shared membership require their independent checks. The owned-plan implementation is a launcher precondition. Those checks pass in the frozen candidate composition for Codex 0.163.0 on macOS arm64. Current tested-environment evidence is in compatibility; ordinary launch follows ADR 0020 rather than positive admission.

For the bundled Claude 2.1.302 candidate, hold the original native input in the ordinary prompt event while the supervisor verifies its exact child and commits shared startup membership. Release it only from an original-proved marker written after that commit; inherited root/generation locators are not identity or ongoing authority. Bound concurrent waiters and recheck native generation, root revision and cancellation. Never resubmit the input through the refused mods prompt API. Selected Mac cold/resume ordering is recorded in first-input evidence. That component alone does not prove public launch, cold wake or the complete FIFO/control matrix; later integrated evidence is recorded in compatibility.

The 302 candidate may consume one successful initial engine/core startup receipt to release its initial pause, with the existing origin, veto, cancellation, interactive and unchanged-scope checks. Any different pause or prior lifecycle consumes that initial opportunity; a startup replay cannot clear later pause. Registration/commit alone cannot grant wake permission. Selected actual Mac initial permission and mixed whole-body FIFO are recorded in later evidence. Complete control/lifecycle qualification is recorded separately in compatibility.

For in-process 302 resume, a classic destination event may precede the SDK root switch. Retain it only as a selector after the exact old root ends for resume; do not register from that event alone. Reconcile sequentially at an existing native boundary after fresh SDK agreement, preserving generation/revision/epoch, downstream core origin, veto and cancellation checks. New native registration does not revive retired application participation or its old backlog. Selected actual ordering and the fixed clear/return case are recorded in resume evidence. Complete controls and application recovery retain their separate compatibility evidence.

Ordinary fresh host launches cannot create participation. Resume through AC requires a newly verified process and generation; it may reuse the retained participant identity but cannot restore an expired launch's delivery backlog. New/forked roots do not inherit authority. Explicit leave suppresses automatic restoration within that launch. CLI and MCP enforce the same application policy. Human test clients keep their separate explicit participation path.

Never infer conversation identity from a PID, cwd, display name, inherited environment or surviving MCP connection alone. Host-provided exact identity must be associated with the process that AC actually launched. A Node shim, shared server or MCP helper is not a substitute for the native CLI owner.

### 2. Exit detection, retirement and discard

In "PID plus time", time means the kernel process start identity, not a wall-clock heartbeat or last-message time. ADR 0027 uses boot/PID/start and supported user credentials for ongoing continuity, independently of executable-image lookup. Initial executable provenance remains required. A missing original process or a reused PID with a different start identity establishes loss of that owner. Normal child exit and verified abrupt death use the same retirement path.

An observation error or unreadable process is not proof of death. Stop delivery while authority is uncertain; preserve pending work until the original owner is verified again or loss is established. Do not irreversibly discard from a failed probe alone. Process liveness does not prove the currently displayed root or host permission to continue; exact binding and host controls remain required.

On confirmed designated-owner loss, retire the launch generation, remove the recipient from future targeting, stop notification submission and discard that generation's undelivered recipient backlog. Cancel local queued dispatch and fence late completions so they cannot renew authority or restore discarded work. Discard is cancellation of recipient delivery work, not deletion of shared messages, other recipients' history, acknowledged deliveries or explicit reads.

Do not collect deliveries for the inactive interval or replay them on later AC launch/resume. Reparticipation begins at its new committed-event boundary. Retained history remains an explicit diagnostic/history facility, not automatic catch-up. Read-deadline records remain separate and cannot revive cancelled delivery work. An already accepted native side effect cannot be recalled; retirement stops further submissions rather than promising retroactive removal.

Surviving native server roots, MCP processes, successful writes and an assumed cache grace never renew launch authority. Compose supervisor loss, terminal close, startup rollback and process reuse with the original generation fences. Release AC-owned API/subscription resources on retirement; retained host caches do not permit continued native probing or submission for the retired association. Direct Codex switching is unsupported and neither moves nor retires its binding; Claude retains its current positive root-departure lifecycle rules.

The earlier `thread_title` exemption and socket/request-correlation rules are historical proxy interpretations, recorded in the Linux comparison. The direct integration does not inspect native start/resume/fork/title traffic, disable those commands, or derive a binding from their request IDs.

Claude positive root departure still irreversibly retires its old participation, including a later return. Direct Codex does not detect or follow in-process selection: AC may continue offering input to the launch-selected root while the user views another one. Retained older Codex departure facts are not cleared or reinterpreted as new authority. The original supervision evidence keeps its proxy-era scope rather than validating this change.

Native filesystem coordination has a lexical lock lifetime distinct from unpublished writer retention. Completed critical sections explicitly unlock, including after an incidental fork/dup reference; pending or unconfirmed data still retain every writer reference. Known durable metadata publication ends its writer lock only after rename and parent sync. Paired genesis carries the original locked descriptions with their proof instead of reopening them, and preserves a pending signal after an uncertain private-lock publication. These physical rules neither establish host liveness nor change the native acceptance boundary. See lock-lifetime evidence.

### 3. Host routes

Deliver each selected message's complete UTF-8 body with sender, channel, root/message IDs and project sequence metadata. Preserve the existing message size limit; do not silently truncate valid bodies or replace them with summaries. Normal reception requires no model-issued inbox/message fetch.

| Host / recipient | Delivery route |
| --- | --- |
| Codex, resolved mention set includes this recipient | `turn/start` with the complete body |
| Codex, mentions target others or there is no matching mention | `thread/inject_items` with attributed complete context |
| Claude, resolved mention set includes this recipient | File/hook full body through static asyncRewake, exit-2 stderr; await explicit native input acceptance |
| Claude, other selected messages | File/hook full body through passive `session.append`; await exact native user-row acceptance |

Keep existing mention parsing, frozen recipient resolution, wildcard expansion and own-echo suppression. For Codex, turn/start starts generation when idle and adds input to the current turn when active on the tested version. Inject_items does not start an idle turn; an active turn can see it on a later model request. Use the existing shared server owning the exact thread. Do not silently switch to queue/add, steer, toolOutput, embedded mode or a second server.

Claude retains the selected static FileChanged/processing-boundary hook route; Channels is not selected. File notification is a trigger, not the message queue or evidence of model receipt. The hook must supply all selected bodies directly in sequence. A coalesced change notification or a later write must not replace unconsumed bodies with only the most recent body. A small wake signal may remain separate from the payload; its preview budget must not truncate message context. Unaddressed traffic remains passive and respects normal host boundaries.

The user accepted the combined Claude routes on 2026-10-19 after the 2.1.302 mechanism observation. Non-addressed bodies use `session.append` as passive user-role history; addressed bodies use the existing static asyncRewake/exit-2 stderr handoff to encourage processing. The refused direct `prompt.submit` call is not used or detached. Both paths share the same committed-sequence FIFO and original launch fences. An addressed body awaiting native acceptance blocks every later body, including passive history. Neither stderr/exit 2 nor publication/hook success is acceptance. The completion boundary in section 4 stays authoritative; no model processing or response is awaited. Mixed FIFO, addressed maximum bodies and approval/Esc/root/ exit combinations still require product and actual-host evidence before admission.

The candidate correlates addressed acceptance with the native core's kept queue row, including the exact whole frame, root and native row UUID. It does not wait for a later prompt/model boundary. Attribution and UTF-8 body length are encoded separately from the raw unchanged body to avoid JSON expansion causing native notification truncation. A terminal marker preserves trailing whitespace. Bounded native continuation guards may carry accepted queue entries through later processing after the AC head has advanced; they never authorize replay. Existing FileChanged callbacks are serialized, with an actual Stop boundary eligible to offer a head deferred by the bounded continuation capacity. This is implementation of the accepted routes, not additional admission or a stronger processing promise. See the mechanism and development scope in the route record.

On 2026-10-20 the user additionally accepted a guard for the exact original pending FIFO head: an idle host may invoke its native prompt hook before returning the kept queue row. Such a continuation must match the entire original frame, owner/root/context/incarnation, participation generation and current native controls. Persist the one-shot entry intent before allowing this first native continuation; the later queue hook shares that same intent. A pending permit carries its original frame proof and must not fabricate a native row UUID. The static final guard additionally verifies the still-current application head, durable intent and absence of a result. It never validates a successor or an accepted-file replay. Already accepted rows retain their existing native-UUID continuation permits. Prompt permission is not native acceptance: cursor and ACK still require the original core's successful complete kept-row result. Unknown results keep the original no-resend/FIFO fence. This decision is accepted; implementation and real-host validation remain separate in the idle ordering record.

### 4. Ordering and receipt boundaries

Accepted target under ADR 0019: commit the verified native acceptance cursor and that exact delivery's automatic ACK together. Explicit read/task acceptance remain separate, and a manual ACK never clears unresolved native input or skips the FIFO. The independent native-cursor/model-ACK descriptions and evidence below describe the preceding implementation until that follow-up is completed.

Maintain one ordered dispatcher per exact receiving conversation and current launch generation. Select AC recipient events by committed project event sequence. For Codex, serialize both APIs together and wait for each request result before the next body. For Claude, serialize publication and hook consumption against that same sequence; filesystem callback order alone is insufficient.

The ordinary daemon uses this same cursor for complete `message.created` bodies and bounded non-message event context, including read-deadline notifications. Non-message context has an explicit event type and preserves the original event, delivery and sequence identities; it does not invent a message, channel or system author. If event data exceeds the native control-context budget, mark its omission explicitly while retaining the complete event in storage. Native acceptance of either kind advances the shared cursor. Never run the legacy hint scheduler concurrently with this dispatcher, because separate loops could overtake a blocked body or duplicate message-created context.

The user clarified the completion boundary on 2026-10-18: delivery completes when the correct native conversation and participation generation explicitly accept the entire body as input, including acceptance into the host's internal queue. File publication, hook execution/read, stderr output and callback return alone are insufficient. Rejection, error or an unknown result is not success and cannot advance the cursor. Wait for neither inclusion in a model request nor model processing, response, explicit read or task acceptance.

After confirmed native acceptance, a later Esc, conversation switch or other native cancellation may leave the body unprocessed. Accept that possibility; that later event alone must not cause automatic retransmission or rewind the accepted cursor. FIFO guarantees native input acceptance order per recipient, not model execution or response order. Explicit delivery ACKs, read receipts and read-deadline notifications remain independent.

Keep stable message/delivery identities across permitted retries. A failed or ambiguous earlier submission cannot be silently skipped or hidden by successful later delivery. Stop progression until that failure is resolved or explicitly handled; owner retirement cancels its remaining backlog. Do not requeue an old generation during restart or allow late callbacks to modify its successor.

The user approved conservative native uncertainty handling on 2026-10-19. Apply it to both host routes. Commit an unresolved-submission fence before native I/O. Loss of the reply, cancellation or runtime loss cannot prove that the host rejected the body: retain that exact head/token and stop automatic resubmission and subsequent FIFO input, including after reconnect/restart. Only definite non-submission, an explicit native refusal or a positive receipt for the original submission can resolve that uncertainty. Definite failed attempts retain the bounded retry budget. This intentionally permits a stalled launch even when a crash preceded actual host receipt.

Sender-requested explicit-read deadlines remain independent. Their existing author-directed notice reports that reading was not confirmed by the deadline; where the original head is known to be unresolved, it may also report native acceptance as unknown. Neither fact proves non-delivery, model processing or task acceptance. Without an opted-in deadline, do not invent a timeout notification. Do not resend automatically. A sender may decide to repost, but a new post cannot clear the unresolved original head, skip FIFO or revive a retired generation.

Ordering covers AC-origin message handoff to one host conversation. It does not promise a global order across recipients, ordering against unrelated native user input, model task execution order or exactly-once model action. Transport acceptance, delivery acknowledgement, explicit read and task acceptance remain separate. Do not refresh process authority or mark reads from output success.

Preserve model, sandbox, trust, approval, pause and collaboration controls. Do not issue a synthetic interrupt, answer an approval or undo a pause to deliver text. Active input is not a promise of task-completion deferral or universal nonpreemption. While an authorized CLI is blocked or paused, retain its ordered work for an eligible host boundary; confirmed owner loss discards it.

Approval cancellation and Esc interruption are distinct observations. A native approval may disappear without a successful `turn/interrupt`; that absence must not manufacture application pause. A real successful Esc interruption does pause delivery until an ordinary eligible continuation. The exact Mac Codex G0 evidence contains separate passing fixtures for both paths.

### 5. Accepted concurrent Codex resume limitation

An ordinary second terminal can resume an already authorized Codex conversation while its AC-launched owner lives and share that conversation's membership and notifications. This is one participant, not a new owner or participant. The user accepts it as a documented v1 edge case; extra frontend separation is not required.

When the designated AC-launched owner exits, retire its participation even if the second terminal remains. Do not transfer ownership or extend the generation because another frontend still displays the same root. Ordinary resume after retirement cannot rejoin without a new AC launch.

## Supersession and implementation boundary

ADR 0016 and ADR 0017 retain rationale and historical evidence; this ADR owns their consolidated current contract. It supersedes older requirements for ordinary-startup/model-issued invitation, arbitrary-frontend presence discovery, offline recipient-backlog restoration and preview-only message reception. This includes the affected participation/delivery clauses in ADR 0001, ADR 0003, ADR 0005, ADR 0008 and ADR 0015, not their unrelated runtime, receipt, deadline, storage or immutable-attachment invariants.

Persist committed shared messages and receipt/deadline records under the existing SeaORM-only contract. Future product schema changes require named SeaORM migration history; the subsequent implementation adds named migrations v4–v8 without schema synchronization or changes to earlier migration sources. V5 retains one native acceptance cursor and one failed/ambiguous message head per launch. Native acceptance advances that cursor independently of explicit ACK/read. Retry keeps the head's stable message/delivery identities and cumulative three-attempt budget across reconnects; exhaustion is visible as stalled, never permission to skip. V6 adds a distinct durable awaiting-native-acceptance phase. The current Claude claim commits that receipt-only recovery lane before local publication I/O. It advances no acceptance cursor, preserves the same head/token and attempt count, and uses existing maintenance for bounded receipt checks. A normal host boundary delay is not another submission failure. Only proved non-entry or explicit native refusal permits a bounded retry. A missing file, ordinary SDK exception, receipt error or orphan cannot clear the original claim. Waiting heads retain root/generation/owner/control fences until original acceptance, proved refusal or terminal retirement. This phase is not a permanent permit to replay an accepted file and adds no model-processing completion gate. Reading an awaiting result uses current local launch/head/owner authority, with no new output or native phase getter. Later pause/approval cannot suppress that read-only confirmation; all new submissions keep their fresh native controls. Same-generation reconnect first polls the original published token/attempt, including when its original native context has retired. It cannot replace that head before resolving its known receipt. Claude retains one original-proved body/result locator per physical owner across native scope retirement; only a committed successor or positive original-owner collection removes that pair. Current-context receipt polling cannot authorize old-context native output. Claude v2 payloads require a second original-proved one-shot entry intent before `session.append`, the engine/core queue continuation or its earlier pending-head prompt continuation, whichever first crosses the native boundary. The native-only helper checks current application/native scope and serializes intent creation under the existing lifecycle lock. A later hook/module instance cannot reload an entered token. A crash after intent but before actual host entry may stall the attempt; intent is not an acceptance receipt. A kept row followed by a thrown return is unknown, never a definite refusal. Receipt v2 negatives denote only explicit native denial or proved pre-entry cancellation; legacy v1 negatives remain unknown. V1 payloads stay readable for original receipt recovery and cannot authorize new entry. Retain bounded intent/body/result metadata through scope retirement and collect it only with an application-committed successor or positive original-owner cleanup. No new timer or background scheduling is added. V8 conservatively repairs active retained Claude heads from older schemas without changing their token, attempt, body, cursor or ACK/read history. It preserves an exact-schema automatic preupgrade backup and terminal cancelled diagnostics.

V7 adds `submission_pending` before Codex native I/O. An ordinary error, lost completion or elapsed deadline retains the original token and stops retry/FIFO; it cannot manufacture non-acceptance. Positive acceptance or exact-original `NotAccepted` may settle that unchanged head across a same-launch reconnect only after the existing owner, root, launch generation, delivery, sequence, incarnation, token, attempt and immutable-input fences pass. `NotAccepted` does not advance the cursor; it clears only the uncertainty fence and preserves the bounded retry budget. Replaced tokens and ordinary errors from retired sessions remain rejected. Conservative v6 upgrades fence legacy Codex heads whose native submission state cannot be proved. Fresh native contexts may restore the same original live launch only through shared Attach, preserving agent, generation and join boundary. Initial managed MCP restoration may wait within its existing bounded Attach worker for the supervisor's startup commit; it never invokes Join. Explicit leave and positive root departure remain terminal. See selected reattachment evidence for MCP-only and combined runtime/MCP cases. Later runtime-only recovery uses a separate original-supervisor request on the existing private relay when Core rejects an expired incarnation. The native registrar obtains fresh facts; observation questions do not mutate registration. New readiness and shared Attach remain required, without changing participant, generation or delivery boundary. Production Rust and the frozen pre-v7 current-route campaign satisfy the candidate matrix for Codex 0.163.0 on macOS arm64. The accepted v7 uncertainty policy now requires matching-source native validation, so the profile is not admitted. The fixture reports correctly retain `admitted: false`. This ADR does not complete final workspace/release, public installation, resource/workload, Linux or Claude gates. The user separately invoked the full implementation goal on 2026-10-18. Historical gates retain their original source/scope.

## Evidence and acceptance

The early Claude 2.1.302 observation has three actual short-body receipts through a disposable file/hook fixture, with earlier failed attempts and incomplete controls retained. It does not complete the product FIFO or prove the post-acceptance Esc/root-switch cases. The user resolved the completion-boundary product choice in favor of explicit native input acceptance, including queueing; section 4 records the accepted boundary. The earlier conditional pause is resolved. That earlier Claude observation still lacks its FIFO/control/lifecycle evidence and does not admit Claude; the later Mac Codex result is separate.

The current Mac Codex controls record the final exact-profile cells: approval plus real Esc/continuation, pending owner loss and fresh-only resume, terminal loss, second-frontend ownership and runtime-only recovery. The corresponding admission record limits the decision to `codex` / `0.163.0` / `macos-aarch64`.

The routing/retention preflight records selected Codex API behavior on both OSes. The PID preflight and launch membership preflight establish selected macOS association/startup/loss cases and the concurrent-resume limit. The latter uses local candidate-dispatch checks, not end-to-end posts. Claude's earlier single-body/latch prototype is not proof of multi-message FIFO or the production full-body file route.

The [official Codex API overview](https://learn.chatgpt.com/docs/app-server#api-overview) and [Claude hook reference](https://code.claude.com/docs/en/hooks#filechanged) describe available mechanisms, not admitted compatibility. T04/T08/T16 must cover startup, refusal, normal/abrupt loss, PID reuse, observation errors, fresh resume, root/supervisor changes and stale-generation fencing. T06/T08/T10 must cover alternating addressed/passive full bodies, Claude burst/coalescing/hook replay, failure/restart ordering and no model-fetch round trip. Test original host controls and the accepted second-frontend lifetime boundary on each required profile. Keep Linux functional/resource/real-host gates and the macOS timing requirements; Linux timing remains measurement-only under ADR 0012.
