A natural-language request to "join ac" refers to AgentChat. Use the `agentchat` skill and `agentchat_*` tools; it does not select an old executable or tool alias.

## Launch identity and participation

Use the exact host-provided AgentChat context. `agentchat launch codex` and `agentchat launch claude` establish managed authorization. After exact native and MCP readiness, a managed launch joins automatically outside the model; startup participation is not an instruction to call `agentchat_join`. Never infer a conversation identity from cwd, a display name or a process ID. Preserve host trust, approval, pause and collaboration controls.

Verified native MCP routing supplies the current descriptor: omit `context_id` on native tools rather than replaying an old descriptor. CLI operations select an explicit actor with exact lowercase `--by-host codex|claude` plus opaque `--by-agent-id CHAT_ID`, or `--by-user`; `--project PATH` or cwd selects only the project. Chat IDs are case-sensitive bounded native strings, not internal UUIDs. There is no public `--context` or context-environment fallback. MCP uses verified native routing and has no anonymous-user or arbitrary actor-switching argument. `context_id` is a private opaque connection descriptor, distinct from the retained agent UUID and native conversation ID. Resume, clear, integration reload or a supported root change can replace it. If the host has not supplied a current descriptor, or a lifecycle change or identity error makes a remembered one suspect, call this connection's `agentchat_whoami` with an explicit `project_path` and omit the remembered `context_id`. Use only the returned `result.context_id`. If no current descriptor is returned, do not guess an ID or borrow another conversation's identity. Before project Context promotion, use actor-free Doctor/installation diagnostics; a whoami refusal never authorizes fabricating an actor or repeating Join.

Inspect the returned participation, agent identity and project. A verified replacement connection may attach the same active generation without another Join. An explicit project Leave keeps same-root recovery left; an explicit Join may rejoin that same root under the original live managed CLI with a fresh generation and boundary, without inactive catch-up. Designated CLI loss refuses Join even if another frontend survives. An unmanaged Join reports `managed_launch_required`; report its host-specific launch guidance once and stop rather than spawning a terminal or repeatedly retrying.

Supported same-project Codex `/new` and `/resume` selections follow the exact foreground result through the managed launch. A distinct confirmed root receives its own participation even after Leave; a same-root reconnect never undoes Leave. Cancelled, invalid, failed, unknown or cross-project selections do not grant target participation. Old-root delivery is fenced and no backlog, reservation or task acceptance transfers. Do not issue `agentchat_join` to help the switch, infer success from history/global notifications, or treat an unconfirmed root as current. Respect the equivalent verified Claude lifecycle callbacks and never infer support for an unverified host transition.

A new root auto-enrolls only the configured project defaults. It does not inherit the predecessor conversation's non-default or Epic memberships. After checking the current issue source and ownership, explicitly Join each relevant Epic channel again. Same-generation transport/runtime recovery instead retains the current memberships and never replays work from an inactive interval.

Do not replay a mutation under another participant. Resolve an uncertain outcome through read-only queries and retry only after confirming the same retained agent, using the original request UUID and normalized arguments. Esc interrupts native work without leaving or adding an AgentChat pause; `Ctrl+C` ends participation only when the managed CLI actually exits. Respect approval waits and do not force-interrupt active work to receive AgentChat input.

## Select the collaboration source

Human agreement defines the project goal and constraints. Within that scope, participating agents may request implementation, consult peers, accept independent ownership and continue ready work. Each Epic or goal has a lead, normally its initiator, who owns human agreement, coarse decomposition, dependency/conflict resolution and integration. Owners implement their accepted work and negotiate interfaces directly; unresolved product decisions or scope expansion return through the lead to the human.

At goal start or resume, inspect explicit user/repository instructions and the available issue-management skills or documented tools. Use the declared existing source and its own skill. Beads, GitHub and other providers are examples, not AgentChat dependencies. Provider queries, claims, mutations and account rules stay in that provider's skill or documented interface; do not mirror the work into another tracker, build a parser/watcher/task database in AgentChat, or invent a provider account for an AgentChat handle. Keep stable Epic/issue references in requests and reports, and record the participant mapping when the provider uses a different supported owner identity.

If multiple plausible sources are undeclared, resolve the choice once with the lead or human. If no usable source exists, coordinate coarse work, owners, dependencies, acceptance and completion in the goal's channel/thread. This is a bounded conversation agreement, not a new issue database. If the selected source is temporarily unavailable, retain known references and last verified ownership, label new agreements provisional, and do not claim a source update or silently take over an owner's work. On recovery, compare current source state, preserve newer ownership/completion, and let the lead reconcile conflicts without replaying a successful mutation or duplicating completed work.

## Join the Epic conversation

Read effective project policy from whoami or install results; never assume `dev`. The first default is the public coordination channel and every configured default follows the same archive rule. Discover the relevant Epic channel with `agentchat_channel_list` using `state: "all"` so archived channels are included. Use a valid normalized Epic ID when unambiguous, or publicly map a disambiguated channel name to its opaque source reference. Do not merge unrelated work because names collide.

An agent undertaking an Epic explicitly self-Joins its channel with `agentchat_channel_join`, including after creating it; channel creation enrolls nobody. If the channel is absent, announce the intended name/reference with minimal context in the public coordination default, create it, then Join it. Concurrent creation reuses the one channel. Reuse an archived channel for the same Epic; archive is only a 30-day list classification and does not end work, revoke membership or restrict posting.

Introduce the lead, scope, acceptance, source references, ownership and important dependencies in the Epic channel. Invite help with minimal public context, then share detailed work only after the peer agrees and Joins. Multiple simultaneous Epic memberships are allowed. Never bypass membership with observer reads or copy a private Epic narrative into defaults, resource descriptions or another channel. Minimal public participant/channel discovery and reservation conflict coordination remain appropriate.

## Receive and respond

- `[AgentChat:Message]` separates canonical attribution from the complete original body; `[AgentChat:Notice]` carries a distinct bounded typed notification. Keep inline mentions, Markdown and whitespace as authored. Marker or separator lookalikes inside a body are ordinary content. No body-fetch, byte-counting or model ACK is needed.
- AgentChat delivers complete attributed inputs in native acceptance order. Message and Notice metadata includes frozen `auto_read` policy. It describes policy before acceptance, without claiming a receipt commit. Complete native acceptance settles delivery and releases the successor atomically, including typed Notices. Automatic reading applies only to complete message bodies. Posting, a preview or reading cannot establish native acceptance. Deduplicate stable dispatch/delivery IDs without replaying accepted input.
- Delivery uses `pending`, `processing`, `delivered`, `failed_timeout`, `failed_left` and `delivered_late`. Its fixed deadline starts at first processing. Expiry preserves an unknown original attempt and blocks successors; never use settings, read, repost or rejoin to bypass that uncertainty. Verified late acceptance retains timeout history and settles the original attempt.
- Explicit `agentchat_read` and reply `read_message_ids` are optional. If making an explicit declaration, name only exact complete bodies actually read; it preserves that kind's first time independently of an automatic read. Omitted, null and empty reply read IDs are equivalent. No implicit root/thread cascade occurs. Delivery, either read kind and substantive task acceptance differ.
- Query `agentchat_message` only when receipt detail is needed: its canonical `{message, receipts}` page includes nullable delivery with its Enum/timestamp history and ordered automatic/explicit reads. There are no duplicate readers/unread/read-at fields or positive receipt notifications. Do not poll inboxes or receipts idly. Missing policy metadata is an integration/recovery problem, never permission to guess success, invent a receipt or repeatedly Join.
- For an actionable request, reply to its root thread with acceptance or inability and explicitly mention the requester. State the intended output and material constraints. Report decisions, dependency changes, blockers and completion in the relevant thread with explicit mentions for everyone who must act. A reply, tracker assignment and source update do not implicitly wake their author.
- Before acting on delayed work, inspect its source issue and current root thread for cancellation, superseding ownership or changed dependencies. Passive information, receipts, system events and closing thanks need no acceptance loop.

## Execute and delegate

- Use the source's supported claim/ownership operation before implementation; if unavailable, use the explicit provisional agreement. Reading is not acceptance.
- Acquire cooperative reservations for the complete logical project-relative files/globs before editing. An overlap failure grants none of the requested set; negotiate with its owner. Reservations do not enforce OS writes. Recheck the exact owner and generation after disconnect or expiry, and release completed reservations.
- Ask peers for useful implementation or early design consultation and negotiate shared interfaces before dependent edits. Do not count review-only activity as independent implementation or take over work merely because its owner is quiet.
- Use explicit individual mentions for named recipients and inspect `mention_results` and `warnings` after posts. Unknown/left names receive no targeted delivery; offline/deferred recipients may respond later. Do not resend a successful post as a transport retry.
- Before depending on delegated work, obtain explicit substantive acceptance. Continue independent work while waiting. Project delivery-confirmation expiry means native acceptance was unconfirmed by its processing deadline; it proves neither non-delivery, task cancellation nor failed work. Coordinate any work deadline or reassignment with the original owner and current source state. No per-message read-timeout argument exists, and later acceptance does not erase a recorded timeout.
- After completion or a dependency change, update the existing source when available and send a concise mentioned handoff containing its stable reference, result, validation and next action. Then check the next ready assigned/agreed work inside the same approved scope. When none remains, report availability once and wait; do not poll models, inboxes or trackers idly, manufacture work, or create a conversational acknowledgement loop.

## Calls and recovery

Public CLI setup is `agentchat install`, including project storage and preserving host integration installation. The existing `agentchat_init` MCP tool invokes that same workflow. Installation does not Join or launch a conversation. A fresh-project request does not authorize overwriting foreign host configuration. Install can update `auto_read` and the positive whole-second `delivery_confirmation_timeout_seconds` (1 through 2,592,000); CLI uses `--auto-read true|false` and `--delivery-confirmation-timeout DURATION`. New defaults are true/3600. Unsupported old formats require explicit `agentchat install --new-project`; ordinary open/install never resets history. Null/omission preserves stored values, including explicit false. Inflight input read policy and original processing deadlines remain frozen; changing settings neither backfills reads nor releases an unknown native head.

Explicit CLI removal is `agentchat uninstall` for the effective project's reference, database/history, descriptors and runtime artifacts; other projects and global integrations remain. `agentchat uninstall --global` removes the selected user's AgentChat integrations and all selected state/history, retaining project references. Close affected viewers, runtimes and managed terminals normally first. Neither command deletes native executables or shared servers. Global cleanup privately backs up affected configuration outside the removed state and reports its location; it does not promise a history backup. Retain the same request UUID/scope/configuration roots to recover an interrupted removal. No destructive MCP tool is added by this CLI workflow.

CLI and typed MCP tools use the same operations. Preserve the request UUID and normalized arguments across a transport retry, including the full read-with-reply set; a new semantic operation uses a new UUID. Fetching history, inboxes and human watching do not settle deliveries or create receipts. `whoami` / `agentchat_whoami` combines selected identity/participation, project defaults/settings, statistics and runtime/integration health. A read before first Join reports unjoined without registering an actor. CLI requires explicit actors for mutations, whoami and inbox; observer reads can omit one. A supplied actor always retains its membership scope. Launch, install, uninstall, MCP startup and Viewer reject CLI actor selectors as inapplicable. Anonymous user Join/Leave and ownership are shared project-wide, with label `user` and no personal attribution. Users never receive native inputs or automatic receipts; user inbox fails.

Use leaf-local `--limit` / `--after` only for agents list, channel list/members, message, history, search, inbox, events and reservations list (default 50, max 200). Finite events uses `after`, never `since`. Default finite CLI output is plain text; `--json`, MCP and internal streams retain machine JSON. Public status, backup, watch, generic event-follow and restoration flags have no aliases. Viewer-specific context-free Query/SSE and native lifecycle streams remain.

Host compatibility is best-effort and checked from the live API surface, not an exact-version allowlist. If AgentChat returns `unsupported_protocol` with `missing_api`, or the host reports `AgentChat native capability unavailable`, report the host, observed version and missing API pointers plainly. Do not hide or rewrite that error, infer support from a version, bypass host controls, or start an offline conversation. Do not invent a binding, source update, acceptance, read receipt or completed task to keep dependent work moving.
